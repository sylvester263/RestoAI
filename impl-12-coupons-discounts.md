# Implementation 12 — Coupons & Discounts

## Goal
Promo codes and automatic offers, usable across WhatsApp and the public web app — table-stakes for any food-ordering platform, currently absent from every existing spec and the codebase.

## Data Model — New Table

```sql
CREATE TABLE coupons (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID NOT NULL REFERENCES tenants(id),
  code VARCHAR(30) NOT NULL,
  type VARCHAR(20) NOT NULL CHECK (type IN ('percentage','flat','free_delivery','bogo')),
  value NUMERIC(10,2), -- percentage, flat amount, or null for free_delivery/bogo
  min_order_amount NUMERIC(10,2) DEFAULT 0,
  max_discount_amount NUMERIC(10,2), -- cap for percentage discounts, nullable = uncapped
  usage_limit_total INTEGER, -- nullable = unlimited
  usage_limit_per_customer INTEGER DEFAULT 1,
  first_order_only BOOLEAN NOT NULL DEFAULT false, -- research-validated pattern: new-customer-only codes
  referral_customer_id UUID REFERENCES customers(id), -- set when this code was generated by a referral program (1.1 below), null otherwise
  starts_at TIMESTAMPTZ,
  expires_at TIMESTAMPTZ,
  active BOOLEAN NOT NULL DEFAULT true,
  created_at TIMESTAMPTZ DEFAULT now(),
  UNIQUE(tenant_id, code)
);

CREATE TABLE coupon_redemptions (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  coupon_id UUID NOT NULL REFERENCES coupons(id),
  customer_id UUID NOT NULL REFERENCES customers(id),
  order_id UUID NOT NULL REFERENCES orders(id),
  discount_applied NUMERIC(10,2) NOT NULL,
  redeemed_at TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX idx_coupon_redemptions_coupon ON coupon_redemptions(coupon_id);
CREATE INDEX idx_coupon_redemptions_customer ON coupon_redemptions(customer_id);
```

### 1.1 Referral program (research-validated addition — a distinct, high-performing pattern from every major delivery platform, not just a coupon variant)
```sql
CREATE TABLE referral_rewards (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID NOT NULL REFERENCES tenants(id),
  referrer_customer_id UUID NOT NULL REFERENCES customers(id),
  referred_customer_id UUID REFERENCES customers(id), -- null until the referred person actually orders
  referrer_coupon_id UUID REFERENCES coupons(id), -- the reward issued to the referrer once earned
  referred_coupon_id UUID REFERENCES coupons(id), -- the first-order discount given to the new customer
  status VARCHAR(20) NOT NULL DEFAULT 'pending' CHECK (status IN ('pending','completed','expired')),
  created_at TIMESTAMPTZ DEFAULT now()
);
```
Pattern (matches Instacart/UberEats research): a customer shares a personal referral link/code; a new customer who orders using it gets a first-order discount (`coupons.first_order_only=true`); once that new customer's order completes, the referrer earns their own reward coupon. This is two coupons and one tracking row per successful referral, not a separate discount mechanism — it composes with the coupon system already specced rather than replacing any of it.

### 1.2 Tiered spend-based discounts (research-validated — "spend more, save more")
Handled without a new table: a single `coupons` row can express "10% off Rs. 1000+" via existing `min_order_amount` + `value`. For a true multi-tier single promotion ("10% off $75, 15% off $100, 20% off $150+" as one promotion), either create multiple coupon rows sharing a common code-family prefix (simpler, recommended for this pass) or add an optional `tier_rules JSONB` column to `coupons` for a single-code multi-tier promotion — recommend the simpler multiple-rows approach first; only add tier_rules complexity if a real product need for single-code tiering emerges.

## API Endpoints

| Endpoint | Method | Auth | Purpose |
|---|---|---|---|
| `/api/coupons` | GET/POST/PUT | Authenticated (owner/manager) | Manage coupons |
| `/api/public/:tenantSlug/coupons/validate` | POST | Public | Validate a code against a cart before checkout |

## Step-by-Step Implementation

1. **Migrations:** Add `coupons`, `coupon_redemptions` tables.
2. **Backend — `server/src/routes/coupons.js` (new, admin side):** Standard CRUD for coupon creation/editing, tenant-scoped like everything else.
3. **Validation logic — shared function, not duplicated per caller:** Write a single `validateAndApplyCoupon(tenantId, customerId, code, cartTotal)` function in a service file (not inline in a route handler) that checks, in order: code exists and belongs to this tenant, `active=true`, current time within `starts_at`/`expires_at` if set, `cartTotal >= min_order_amount`, usage limits not exceeded (query `coupon_redemptions` count both total and per-customer). Return the computed discount amount (respecting `max_discount_amount` cap for percentage type) or a clear rejection reason. This function must be callable from both the public checkout flow AND the WhatsApp order flow — do not write two separate implementations.
4. **Public endpoint:** `POST /api/public/:tenantSlug/coupons/validate` — resolve tenant by slug (never client-supplied), call the shared validation function, return the discount amount or rejection reason. Do not actually record a redemption here — only at final order confirmation (step 5), so an abandoned checkout doesn't burn a usage slot.
5. **Order creation integration (`orders.js` shared service):** When an order is created with a coupon code attached, re-validate (never trust a discount amount passed from the client — always recompute server-side at order-creation time, same principle as payment amounts must never be trusted from the client), apply the discount to the final total, and insert a `coupon_redemptions` row in the same transaction as order creation (so a failed order never consumes a coupon usage).
6. **Concurrency correctness:** Usage-limit checking is a read-then-write pattern (count existing redemptions, then insert a new one) — apply the same row-locking discipline already established as a standing rule in this codebase (see `PROJECT-MASTER.md` Section 3) to prevent two simultaneous orders both squeaking through a coupon's last remaining use.
7. **Frontend — admin `client/src/pages/Coupons.jsx` (new):** Create/edit coupons (code, type, value, min order, usage limits, date range), list view with redemption counts.
8. **Frontend — public checkout (`Checkout.jsx`):** Add a promo code input field, call the validate endpoint on entry (debounced), show the resulting discount applied to the order summary before final confirmation, show a clear rejection message if invalid/expired/limit-reached.
9. **WhatsApp integration:** Extend the order-parsing agent to recognize a coupon code mentioned in a message ("apply code WELCOME10"), call the same shared validation function, and reflect the discount in the order confirmation summary already built (per `impl-01`'s confirmation-before-finalizing flow).
10. **`first_order_only` enforcement:** in the shared validation function (step 3), if a coupon has `first_order_only=true`, check the customer has zero prior completed orders for this tenant before allowing redemption — reject with a clear reason otherwise.
11. **Referral program (Section 1.1):** a customer-facing "invite a friend" surface (could live on the loyalty page already built in `impl-03`, or the order tracking/confirmation screen) generates a personal referral code tied to a `referral_rewards` row. When a new customer places their first order using that code: apply their `referred_coupon_id` discount as normal, mark the `referral_rewards` row's `referred_customer_id`. Once that order reaches `delivered`/`completed` (not just placed — guard against referral-then-immediately-cancel abuse, same spirit as the fraud-detection agent's `rapid_reorder`/`repeat_cancel` checks in `impl-21`), issue the referrer their reward coupon and mark the row `completed`.

## Verification Steps
1. Create a percentage coupon with a cap, apply it to a cart above the minimum order amount, confirm the discount is calculated and capped correctly.
2. Attempt to use an expired coupon — confirm it's rejected with a clear message.
3. Attempt to exceed `usage_limit_per_customer` with the same customer — confirm the second attempt is rejected.
4. Fire 5 concurrent checkout attempts against a coupon with `usage_limit_total=1` — confirm exactly 1 succeeds (same concurrency test pattern already used for the loyalty redemption fix).
5. Confirm an abandoned checkout (validated but never completed) does not consume a usage slot.
6. Apply a coupon via WhatsApp order flow, confirm it's reflected correctly in the pre-finalization confirmation summary and the final order total.

## Explicitly out of scope for this file
- Auto-applied offers with no code (e.g. "10% off orders over Rs. 1000, no code needed") — code-based coupons only for this pass, though the `coupons` table could support this later by making `code` optional
- Stacking multiple coupons on one order — one coupon per order for this pass
